## 方法变化

先决定注意力顺序、构图、光线和明暗分离、材质响应、配色关系及不应出现的元素，再编写图片描述。已选方向通过局部修复保留，不因一个缺陷重做整个场景。获准比较候选时，比较不同设计假设，而非把随机重抽包装成多个视觉方向。

区分动作分镜板、视觉定调图与实际生产控制帧。本补丁保留用户选定的四格板工作流，不会偷偷裁格或增加生成。明确要求独立主视觉或首尾控制帧的任务仍使用其指定格式。未将默认四格流程切换为另一套 agent 配置。

特效先明确意图、目标、保留区域、触发、可见变化、结束状态、运镜/遮挡关系、真实输入与失败条件，再编译进实际 prompt。特效卡片描述不是已验证的制作配方。允许所选特效在明确范围内发生形变，禁止未经请求的主体漂移；避免“整体融化但轮廓完全不变”等自相矛盾要求。

质量检查受既有预算和媒体可访问性限制，不新增应用中的“质量模式”开关。读取抽帧不等于完整观看视频；完成状态不等于视觉验收。方法中的要求不是代码层的确定性拦截器。

## 让新版真正生效

基准版本的 `skills/storage.rs` 使用 `INSERT OR IGNORE` 初始化文档，运行时从数据库读取。这意味着更新磁盘上的旧文件并重启，不会覆盖已有数据库正文。

新安装或独立测试配置：按项目现有启动方式加载该分支及其 `skills/` 资源，将实际读取正文与所选 Git 提交的对应文件比较。不要把测试数据库替换进日常项目。

已有安装：先备份自己的规则修改。通过现有技能文档读取/保存机制，将上述五个 `SKILL.md` 及分镜视频 `CORE.md` 的改动合并到对应数据库文档；不要覆盖用户自定义内容而不比较。新方法文档在应用启动时应由既有目录扫描插入；已经存在的同名文档也需要核对和更新。保留修订号校验，遇到版本冲突先重新读取再合并。

逐一读取五份入口、五份新方法及修改后的 `CORE.md`的**运行时正文**。未自定义的文档应与所选 Git 提交的对应文件逐字比较或比较 SHA-256；有自定义内容的文档应核对合并差异，确认新增方法规则与链接已保留，并确认 `CORE.md` 已区分 shot-board 与 standalone 任务。不要为验证接入而在 Skill 中添加交付回执。仅查看 Git 文件、看到新增方法文件或看到生成成功，都不能证明入口已经更新。不要删除整个应用数据库来强制刷新规则。

本补丁不增加数据库迁移或自动升级实现。

## 离线检查

在完整仓库中运行：

```sh
python3 scripts/check_skills.py
python3 scripts/test_visual_methods.py
sh scripts/check.sh
```

`test_visual_methods.py` 检查五套入口、新方法链接、根目录隔离、副本同步、英语与文件大小约束、快捷入口中的核心规则、运行时正文不混入交付与测试回执，以及九个编写的案例约束。完整源码存在时，它也调用原有 skill 校验器；原交付包的六文件源码快照不运行该项。`scripts/check.sh` 已接入这些方法检查，源码发布白名单仅新增上述两份公开测试文档，内容扫描继续生效。

这些测试**不会**启动 Mstudio agent、调用模型、观察像素或判断审美。案例中的 `inputs` 是合成输入清单，不是实际素材，路线名称也不是可直接传给 Mstudio 的 API 枚举。`ready-for-authorized-test` 只表示样例按所声明的前提自洽，不表示真实素材或服务已经就绪。

案例 JSON 中的 prompt 是人工编写的参考答案，不是 agent 的运行输出。失败场景的测试检查“编写的计划是否按声明条件标记缺口”，不能证明运行时 agent 一定会正确阻止调用。禁止把这些通过项报告为视频/图片生成效果通过。

## 九个案例

| ID | 场景 | 编写的参考行为 |
|---|---|---|
| 01 | 单幅音频产品主视觉 | 用高光形状、轮廓间隙和背景明暗组织画面，不强制四格 |
| 02 | 已选人像的局部光线修复 | 保留人物、构图、姿态；不把情绪简化为蓝色滤镜 |
| 03 | 饮料罐局部结霜 | 描述生长前缘、薄霜材质、标签保留和结束展示 |
| 04 | 包装消散露出商品 | 包装逐渐失去实体，商品保留；不是在完整包装外堆粒子 |
| 05 | 整体融化但锁定轮廓 | 报告范围冲突，不发送相互矛盾的最终 prompt |
| 06 | 烟雾转场缺后一镜头 | 要求补全转场另一端，不把单镜头烟雾叠加当成转场 |
| 07 | 四格板遇到仅首帧端点 | 报告模式不兼容，不把整板冒充首帧 |
| 08 | 用普通视频参考冒充编辑 | 保留原动作要求，报告所选端点没有已确认的编辑能力 |
| 09 | 指定地点的一镜地面拉远至太空 | 缺地点起始证据时不编造地理一致性，不偷偷增加剪切 |

## 实际模型验证方案：本次未执行

先在独立测试配置确认上述运行时正文版本，再通过当前应用的真实生成流程测试。使用合成商品和有权使用的人像/视频，替换案例中的清单占位；不要上传 API 密钥、生产数据库或真实用户聊天记录。

保留基线配置和新版配置，使用相同产品素材、模型端点、支持的参数、画面比例和总预算。端点支持时记录相同 seed；不支持时记录“不支持”，不要发明字段。记录服务端提示词扩写设置，因为最终提交文本和供应商内部重写不一定相同。

先验证四个不应付费执行的缺口场景：05、06、07、08。观察真实 agent 的回应与真实任务列表，确认没有新增生成任务。不要仅凭参考答案正确就记为通过。

再以 01、03、04 做小范围媒体对照。01 明确要求单幅主视觉；03 使用检查过的独立首尾控制图及支持该模式的端点；04 明确要求独立特效镜头而非四格整板。只有已授权预算包含图片制作时才生成额外控制图。

对每次运行记录：实际入口正文版本、实际读取的方法、真实最终 prompt、参考素材用途和技术角色、模型端点及参数、真实任务 ID、费用、产物及检查范围。没有看到的字段记“不可获取”，不要填推测值。

图片检查结构正确性之外，还要比较焦点、轮廓分离、构图和材质是否兑现已选方向。视频必须实际播放，检查中间过程、运动、闪烁、遮挡、主体漂移和结尾；声音另行检查。可以盲测两两偏好并保留平局，不建立虚假的通用美感分数。

比较同总预算或明确列出成本差异。多抽几次后挑出一张漂亮图，不能证明单次方法改善。保存失败结果及其原因，禁止只报告最好看的样本。
